# William Joseph Craft Boilerplate
This is the boilerplate install for Craft CMS builds at William Joseph. It contains an asset build pipeline, common plugins and a starting template architecture.

## How to use boilerplate
1. Make a website local directory
    - `mkdir folder-name`
1. Enter that directory
    - `cd folder-name`
1. Git clone boilerplate into the directory
    - `git clone https://github.com/WilliamJosephLtd/wj-craft5-boilerplate.git .`
1. Create a new repository on the command line
	- `git init`
    - `git remote set-url origin https://github.com/WilliamJosephLtd/git-repo-url.git`
	- `git push -u origin main`
1. Change the `name` value in `.ddev/config.yaml` to the project name (this will define the dev site URL).
1. Edit the `name`, `description` and `url` values in `package.json`.
1. Check that the databse spec in the DDEV config file matches the one on the server.
1. With Docker Desktop running in the background, run `ddev start`
    - See below **Running the site locally** section for [Docker Desktop](https://www.docker.com/products/docker-desktop/) install
1. Install Craft/plugins
    - `ddev composer install`
1. Create .env file from .env.example
    - `cp .env.example.dev .env`
1. Set up craft (`PRIMARY_SITE_URL` value should be empty in .env)
    - `ddev php craft setup`
    - Follow instructions on terminal
1. Edit .env file.
1. Recreate a Craft license key
    - Delete `config/license.key` file
    - Craft will recreate a new license key automatically
1. Upgrade Craft and plugins to the latest
    - Check available upgrade from Utilities > Updates
    - `ddev composer update`
1. Recreate plugin license keys
    - Delete license keys in the CMS plugin settings (Settings > Plugins)
    - Craft will recreate new license keys automatically
1. Edit and lock the Craft and plugins versions
    - Check plugin versions from Settings > Plugins
    - Edit Craft and plugin versions in composer.json file
1. Edit this README.md file for the new project by doing the following:
    - Edit the title and description at the top.
    - Remove the **How to use boilerplate** section.
    - Edit the **Running the site locally** section.

## Running the site locally
The quickest way to get this site up and running in your local development machine is to use [DDEV](https://ddev.com/). On a Mac;

1. Download and install [Docker Desktop](https://www.docker.com/products/docker-desktop/)
1. Install [DDEV-Local](https://ddev.com/get-started/). If you have Homebrew installed, run `brew tap drud/ddev && brew install ddev`
1. Login to the production CMS, navigate to 'Utilities' in the left hand menu and download (and unzip) a back-up of the production database
1. Clone this Github repository to your machine and open a terminal at the root of the project
1. To create .env file from .env.example, run `cp .env.example.dev .env`
1. With Docker Desktop running in the background, run `ddev start`
1. This will give the URL of the site (e.g. `https://yourprojectname.ddev.site`)
    - If you are running DDEV for the first time, you need to run `mkcert -install` for SSL certificate
1. Import database
    - Run `ddev import-db`
    - enter the file path for the `.sql` or `.zip` database export you downloaded (e.g. `/Users/username/Desktop/craft-boilerplate.sql.zip`)
1. Update the `.env` values (you may need to fetching some from the server)
1. Run `ddev composer install`
1. The website should be running on the URL given (e.g. `https://yourprojectname.ddev.site`)

In the terminal, you should now run any PHP and Craft commands within the DDEV container. For example:
```
ddev php craft project-config/apply
```
If you would like to use `DDEV share` CLI for sharing your local dev site over the internet, run `brew install ngrok/ngrok/ngrok` to install `ngrok`

## Building assets
SCSS, JS and image assets are built using Vite. To begin development;

1. From the project's root directory, run `ddev npm ci` to install the dependencies for the Vite tasks.
    - `ddev npm ci` will install `node_modules` exactly same as `package-lock.json` file.
    - `ddev npm install` may change/update `package-lock.json` file.
1. Run `ddev npm run dev`, to trigger a Vite dev task to build and watch your SCSS, JS and image files located in `./src/` as well as start a Browser-sync which should reflect your Craft development site.
1. Run `ddev npm run build` to build for production.

## Image srcset
Image `srcset` can be generated by using `image srcset macro` in templates.
```
{{ macro.image({
    image: image,
    imageClass: "",
    alt: image.alt,
    lazyLoad: null,
    sizes: [
        { maxScreen: "479px", width: 448, height: null },
        { maxScreen: "767px", width: 688, height: null },
        { maxScreen: "", width: 904, height: null }
    ]
}) }}
```
1. `height` value is optional.
    - if height is specified, the image will be cropped to the size.
    - if height is empty, the image will not be cropped.

## CSS framework
The Tailwind CSS framework has been installed on this site. The Tailwind CSS is compiled when a Vite task is run. The compiled Tailwind CSS only contains classes that are in use in the HTML. The Tailwind documentation gives you lists of classes to use: https://tailwindcss.com/docs/installation

For example, instead of using `width:100%` in the custom CSS, add the class to the tag like this: `<header class="w-full">`

This class then uses the following from the base Tailwind CSS: `.w-full {width:100%}`

### Breakpoints
Every utility class in Tailwind can be applied conditionally at different breakpoints to build responsive interfaces without ever leaving your HTML. We still use a mobile-first approach.

To add a utility but only have it take effect at a certain breakpoint, prefix the class name with the breakpoint name, followed by a colon. This example gives the image a width of 16rem by default, 32rem on medium screens and 48rem on large screens:
`<img class="w-16 md:w-32 lg:w-48" src="...">`

The sizes for the breakpoints are specified in the Tailwind configuration file (`screens` in `tailwind.config.js`). These override Tailwind’s default sizes.

### Spacers (padding and margin)
Tailwind uses the following utilities for padding: `p{t|r|b|l}-{size}`

For example, we use `pt-6` for size 6 padding on the top.

We can also use:
- `p-{size}` for all sides
- `px-{size}` for both `padding-left` and `padding-right`
- `py-{size}` for both `padding-top` and `padding-bottom`

Tailwind uses similar class names for margins – just replace `p` with `m`.

The spacing sizes are set in the Tailwind configuration file (`spacing` in `tailwind.config.js`).

Use the responsive spacing Tailwind classes in the HTML like this:
`<div class="pb-10 social md:pb-10-lg">`

### Hover states
Prefix the class name with `hover:` to have a utility take effect on hover, for example:
`<label class="border block bg-white hover:bg-grey cursor-pointer...`

## Cookie preferences tool
The tool included in this boilerplate will be displayed once a cookie policy entry has been set in the Globals area of the Craft control panel.

Although we don’t use a third-party plugin for the cookie notice itself, we utilise the Cookies plugin by nystudio107 to set and retrieve the cookie set by the cookie notice.

You should be able to set up Google Consent Mode in GTM, but we were unsuccessful when attempting to do so for CAP, so we’re stating that this option isn’t compatible with Google Consent Mode.

Additionally, there is no automatic scanning and categorisation of cookies, so this option is only recommended for websites with a straightforward setup (for example, those that only use Google Analytics).

It’s a manual process to set up the triggers in GTM to set the tracking cookies after consent is given:
1. Open the website’s Google Tag Manager (GTM) container.
1. Select ‘Variables’ to open the variables panel.
1. Select ‘New’ and add a 1st-party cookie variable:
1. Name the variable ‘Cookie Preference Status’.
1. Use the name of the cookie preferences cookie for the variable, e.g. ‘WJ_cookieConsent’.
1. Select ‘Triggers’ to open the triggers panel.
1. Select ‘New’ and add a custom event trigger:
	1. Name the event ‘No Cookie Consent’.
	1. Under ‘Event name’, enter `.*` (full stop and asterisk).
	1. Enable using regex matching.
	1. Select the ‘Some custom events’ option.
	1. Select the variable name ‘Cookie Preference Status’ in the condition settings.
	1. Set the trigger to fire when the cookie does not equal the value set when the visitor gives consent, e.g. allow.
1. Select ‘Tags’ to open the tags panel.
1. Open the settings for any tracking script tags. A tracking script is any script set to track a website visitor, including scripts from Google Analytics, Hotjar, and Facebook/Meta Pixel.
1. Select the ‘Edit’ (pencil icon) in the ‘Triggering’ section.
1. Select ‘Add Exceptions’ and add the cookie consent trigger to the tag as an exception. (If there are already exceptions in the tag, select the plus symbol next to ‘Exceptions’ to add the exception.)
1. Select ‘Submit’ at the top of the screen and then ‘Publish’. You may need to wait for about 20 minutes or so before the tag changes go live.

## Upgrade

### Tailwind
This boilerplate uses Tailwind CSS v4. Key differences from v3:

- **No `tailwind.config.js`** — configuration is now done in CSS using `@theme` inside `src/styles/site.css`. Custom breakpoints, colours, spacing, and fonts are defined there.
- **No `@apply` for unknown utilities** — arbitrary values must use the in-line syntax, e.g. `[clip-path:none]` instead of `@apply clip-path-none`.
- **Breakpoint syntax** — `screen()` is used in CSS media queries instead of `theme(‘screens.md’)`.
- **Utility renames** — some v3 class names changed in v4 (e.g. `shadow-sm` scales differ). Check the [Tailwind v4 upgrade guide](https://tailwindcss.com/docs/upgrade-guide) if a class appears to have no effect.

### Matrix blocks
Use `.eagerly().render()` to render nested matrix entries instead of a manual loop. Craft automatically maps each entry type to its corresponding `comp__<handle>.twig` partial.

For example, the accordions block (`block__accordions.twig`) renders its nested accordion entries like this (`block__accordion` is entry type handle, and `comp__accordion` is the descent field handle.):

```twig
{{ entry.block__accordion.eagerly().render() }}
```

Craft looks up `templates/_partials/entry/comp__accordion.twig` for each entry and renders it — no loop needed. The `.eagerly()` call batch-loads all related entries and their fields in a single query, avoiding N+1 database queries.

The equivalent manual loop (avoid this pattern where possible):

```twig
{% for accordion in entry.block__accordion.all() %}
  {% include "_partials/entry/comp__accordion" %}
{% endfor %}
```
